### 배경 — 역할 재확인 (사용자 지적으로 방향 정정)

>  그 인계 때문에 작업이 커졌다."

맞는 지적이었다. **⑦ 수행이 본체인데 판정 로직부터 만들고 있었다.** 순서를 바로잡았다.

### ⭐ 독립성 원칙 (2026-08-10 확정)

```
QA 작업 (㉮)                          테스트 자동화 (㉯)
분석 → TC 작성 → 수행 → 산출
                  │
                  └─ [넘기기] ─→ finding(coverage-gap) ─→ 유지보수 큐
                     한 방향 · 한 지점
```

- **QA 작업은 카탈로그를 몰라도 완결된다.** 저장·수행은 카탈로그를 건드리지 않는다
- `loadCatalog()`는 **절대 throw하지 않는다** — 실패 시 `null`, 화면은 "카탈로그 없음"만 표시
- 인계는 `finding` 한 줄. 테스트 자동화는 **그 신호만 보고 `tc` 테이블을 들여다보지 않는다**
- **검증**: 카탈로그 파일을 치우고 저장·수행·후보·인계 전 경로가 정상 동작함을 확인

### 판정이 아니라 **검색**이다

자동화할지 말지는 **사람이 정한다**(반복 가치가 있나 / 1회성인가 — 카탈로그와 무관).
시스템은 넘기기 직전 "혹시 이미 있나?"를 찾아줄 뿐이다.

**90건을 다 보라는 건 무리**이므로 세 겹으로 부담을 낮춘다:
1. **카테고리로 좁힘** — 90 → 5~17건 (사람이 훑을 수 있는 양)
2. **유사도로 정렬** — 후보가 위로. **자르지 않는다**(자르면 "없다"는 잘못된 확신을 준다)
3. **되돌릴 수 있음** — 중복이었다면 유지보수 큐에서 빼면 된다

> 정확도 부담이 사라진다. 검색이 틀려도 "비슷한 걸 못 찾음"일 뿐, 결정은 사람이 한다.

## 2026-08-11 (5) — 수행 결과 조용한 실패 버그 수정

사용자가 "TC-012 드롭다운을 Pass로 바꿨는데 새로고침하니 Blocked로 복원"을 보고.

### 원인
`TcPanel.setResult`가 낙관적 갱신 후 POST를 `await`하되 **응답 성공을 확인하지 않았다.**
POST가 실패해도(500·네트워크·dev 서버 재컴파일 중 등) 화면은 낙관값을 유지하고
DB는 옛 값 그대로 → 새로고침하면 DB 값이 로드되어 "결과가 되돌아간 것"처럼 보인다.
CLAUDE.md의 **"조용한 실패 금지"** 원칙 위반.

※ 자동저장이 result를 덮는 것은 아님을 먼저 배제 확인 — upsertTc는 result를
  UPDATE SET에 넣지 않아 사람 값을 보존한다(재현 폴링 6회 전부 보존).

### 수정
`setResult`에 `res.ok` 검사 + 실패 시 **이전 값으로 롤백 + 빨간 flash 경고**.
저장된 것과 화면이 어긋나지 않는다.

### 검증 (Playwright, fetch 인터셉트로 500 강제)
| | 결과 |
|---|---|
| 실패 시 화면 | Pass→**Fail 롤백** (DB와 일치) ✅ |
| 실패 시 통지 | "TC-012 결과 저장 실패…" 배지 노출 ✅ |
| 인터셉트 제거 후 정상 저장 | 화면·DB 모두 반영 ✅ |

교훈: dev 중 코드 수정으로 서버가 재컴파일되는 동안 사용자 조작이 겹치면
이런 조용한 실패가 실제로 난다. 낙관적 UI는 항상 실패 롤백을 짝지어야 한다.

## 2026-08-12 (5) — TC 자동 수행 트리거 (버튼화)

사용자 지적: "TC 수행을 자동으로 하도록 설계했는데 화면에 트리거가 없다."
사실 확인 — 시안·문서엔 "수행 결과 사람 기입"만 있고 자동 수행 트리거는 미문서/미구현이었다
(DV-740 때 내가 스크립트로 1회 수행했을 뿐 버튼 없음). 지적이 정확 → 버튼으로 구현.

### 방식 (사용자 확정)
기존 채팅 파이프라인(Claude Code + Playwright MCP)을 **버튼으로 트리거**. 새 엔진 없음.
- TC 표 헤더에 [▶ 선택 수행 N]·[전체 수행] — picked 체크박스 재사용
- handleRunTc: 선택 TC를 수행 프롬프트로 조립 → handleSend(기존 채팅) → Claude가
  stage(tms-stage.roouty.io)에서 Playwright 수행 → 응답 끝 `| TC-ID | 결과 | 사유 |`
  표를 파싱 → auto-results로 tc 테이블 일괄 기입 → 표 새로고침
- 규칙: 실행 가능→Pass/Fail, 데이터 세팅 필요·명세 미정의→Blocked+사유

### 구현 파일
- repo.setTcResult: note(수행 사유) 옵션 추가 (수동 기입은 note 미전달로 보존)
- tc route: `auto-results` action (local_id 매칭 배치 기입, 미매칭 목록 반환 — 조용한 실패 금지)
- WorkspaceView: handleSend가 응답 반환하도록 수정 + handleRunTc(프롬프트·파싱·기입)
- TcPanel: onRunTc·running prop + [선택/전체 수행] 버튼

### 검증
버튼 렌더·배선·tsc·eslint 통과. ⚠️ 실제 stage 수행(Claude Code CLI + Playwright, 토큰 큼)은
사람이 버튼 눌러야만 돌아서 라이브 트리거는 안 함 — 다음 실사용에서 확인.
